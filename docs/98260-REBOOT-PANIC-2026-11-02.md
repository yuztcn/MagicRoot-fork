# 98260 临时 Root 重启原因（2026-11-02）

## 结论

最近的“进入开发者选项 / 关闭 USB 调试后重启”不是正常重启，也不是 Shizuku 或 ADB Root 开关直接触发，而是 **98260 的 timer-UAF 在 init 收尸子进程时被踩中，触发 kernel panic**。

`reboot` 只是表象；内核记录的真实原因是：

```text
page_request
Internal error: Oops: 0000000096000004 [#1] PREEMPT SMP
Kernel panic - not syncing: Oops: Fatal exception
```

## 与代码注释一致

`run.sh` 的 rootd 清理逻辑明确写过：

```text
# Killing the parent reparents a timer-UAF zombie to init, which panics
# in posix_cpu_timers_exit/rb_next.
```

`98260/run98260.sh` 也明确说明：

```text
# Same-boot parked guard. A failed UAF deliberately leaves the exploit parent
# alive; killing/reaping it can trip posix_cpu_timers_exit.
```

本次 panic 的调用栈正是 `posix_cpu_timers_exit -> rb_next`，与注释完全吻合。

## 不是这些原因

- 不是关闭 USB 调试本身
- 不是 ADB Root 开关
- 不是 Shizuku 库
- 不是 V9 是否需要 Shizuku
- 不是正常的 Android 重启

**根因是 98260 的 timer-UAF 生命周期污染了某个子进程的 timer 树，任何会被 init 收尸的子进程退出都可能踩中。**

## 处理建议

### 短期

- 临时 Root 生效期间不要进入开发者选项、切换 USB 调试/无线调试。
- 必须关闭调试时，先重启设备，再操作。
- 不要 kill 已 park 的 `exploit-android-key-ptr`，不要使用管理器的 soft-reboot。

### 根本修复

需要改 98260 exploit，而不是 UI：

1. Root 成功后，持有被 reclaim 的 timer 页/相关 ring，不再 `destroy_rings()` 或释放给 buddy。
2. 确保 UAF 子进程的 parent 始终存活，不能被 init 接管收尸。
3. 或者避免在 Root 会话内触发 USB gadget 重配置；但这只是绕过，不是修复。

当前版本只能做到 UI/流程层规避，无法阻止内核在收尸时 panic。

## 为什么不能杀 rootd

rootd/`exploit-android-key-ptr` 不是普通后台进程：它持有 timer-UAF
污染过的 task/timer 页面。对它执行 `kill -9` 仍会走内核 `do_exit()` →
`release_task()` → `posix_cpu_timers_exit()`，也就是本次 panic 的同一条路径。

更危险的是：rootd 被杀死后，它的 UAF 子进程会被 reparent 给 init；
init 随后 `wait4()` 收尸时同样会 panic。

所以：

- 不要 `kill rootd`
- 不要 `pkill exploit-android-key-ptr`
- 不要用 cleanup 按钮去真正杀掉 rootd
- 不要用 `ksud soft-reboot`

现有脚本只删除 socket、不杀 rootd，正是为了避开这条 panic。

## 彻底解决路线

### A. 永久 Root（推荐）

放弃 98260 timer-UAF 临时 Root，使用 KernelSU 原生 LKM / 正确 boot 镜像
方案。没有 UAF 页面，就不存在收尸 panic。

### B. 修 98260 exploit 生命周期

在 `binary-sources/98260-6.12/uaf_plant_61258.c` 中：

1. Root 成功后不调用 `destroy_rings()`，不释放被 reclaim 的 timer 页。
2. 不调用 `munmap`/`close_stream` 释放 victim 页所在的映射。
3. 保持 `exploit-android-key-ptr` 父进程和 UAF 子进程存活，永不 reparent 给 init。
4. 保持 rootd 子进程存活到重启。
5. 页面泄漏是预期代价：一个 8 KB 级别的页，换整个 boot 周期稳定。

核心原则：**把被污染的 task/timer 页面永久 pin 住**，而不是试图 kill 或
clean 它。

### C. 内核层规避

用 LKM/kprobe 在 `posix_cpu_timers_exit()`/`rb_next()` 校验并跳过损坏节点，
但风险高，也需要每次内核适配，不如 A/B。

### 唯一安全的退出方式

- 正常完整重启，让内核重新初始化；不能先杀 rootd 再关机。
- 如果重启过程本身 panic，设备仍会复位，但会再次留下 panic 记录。

## 安全清理 rootd：已验证

rootd 不是单一进程：

```text
17792  1      Ss  exploit-android-key-ptr   # UAF 页面持有者，父进程，parked
17800  17792  S   exploit-android-key-ptr   # rootd listener 子进程
```

socket inode 属于 PID 17800：

```text
/data/local/tmp/pc98260-root.sock -> socket:[267491]
17800 fd/4 -> socket:[267491]
```

因此可以只杀 **rootd listener 子进程**：

```sh
kill -9 17800
```

实测结果：

```text
17792  1      Ss  exploit-android-key-ptr
17800  17792  Z   [exploit-android]
```

- 17800 变成 17792 的僵尸
- 17792 仍在 `for (;;) pause()`，不会 `waitpid`
- init 不会收尸
- `release_task()` / `posix_cpu_timers_exit()` 不会执行
- `/system/bin/su -c id` 仍然返回 uid=0
- 没有 panic，没有重启

### 清理规则

1. 先确认 KSU 已经加载，`/system/bin/su -c id` 可用。
2. 通过 `/proc/net/unix` 的 socket inode 找到 rootd listener PID。
3. 只杀这个 listener 子进程，**绝对不要杀它的父进程 17792**。
4. 父进程必须一直 parked 到重启；它持有被污染的 timer 页面。
5. stale socket 文件可以忽略，或由有权限的 init/rootd 上下文 unlink。

### 为什么可行

`posix_cpu_timers_exit()` 在 `release_task()` 里执行，而 `release_task()` 由
父进程收尸触发。rootd 子进程被杀后：

```text
rootd child exit
-> 变成 parent 的 zombie
-> parent 永远 pause，不 waitpid
-> release_task 永远不会被调用
-> timer 树不会被清理
-> 不会 panic
```

### 不能做的事

- 不能杀父进程 17792
- 不能对父进程 `waitpid`/reap
- 不能把父进程 reparent 给 init
- 不能在没有 KSU su 时杀 rootd

### 完整清理

- 用户态：杀 rootd listener 子进程（已验证安全）
- 内核态：父进程和 UAF 页面只能靠重启清除
- 永久解决：KSU 原生 LKM，或修 exploit 让页面永久 pin 住

Latest faultdetect entry before the current boot:

```text

```

Dropbox sequence:

```text

```

There is no `SYSTEM_RESTART` before the 21:00 reboot, so this was an abrupt
kernel panic, not a clean reboot.

This matches the earlier timer-UAF failure mode: `ksud soft-reboot` performs a
userspace stop/start while the 98260 exploit/rootd is parked; process teardown
makes init reap the timer-UAF child, producing `page_request` panic.

The app's `/data/adb/ksu/soft_reboot.lock` directory guard still exists, but
SukiSU's CLI/manager path did not honor this FinaSU-specific guard.  The
external `ksud soft-reboot` cannot be made safe by the app.  Use a full reboot,
never `ksud soft-reboot`, while temporary root is active.

## 2026-11-06 四份 dumplog 复核与修复

### 新增证据

四份 `last_kmsg` 的 fatal 栈均为
`wait4 → release_task → posix_cpu_timers_exit → rb_next`，`lr` 均为
`timerqueue_del+0x38/0x74`。三次 PID 1 panic 前紧邻 `exploit-android` 僵尸回收；
16:10 则由 exploit 自己收尸触发，且当时未加载 KernelSU。这排除了“KSU 或
zygote 是必要条件”，也确认 soft-reboot 是批量收尸的触发/放大因素。

`log.db/event_info` 的 181 次聚合 panic 中，164 次的第二栈帧是
`timerqueue_del`。`history.log` 的 203 条 PANIC 是另一套未去重计数，两者不应混用。

### 已实施的代码修复（尚待真机复验）

1. 6.12.58 exploit 在首个 UAF fork 前启用 `PR_SET_CHILD_SUBREAPER`，并忽略
   SIGHUP/SIGTERM/SIGINT/SIGQUIT。中间子进程退出后，未收尸的 victim/helper
   由仍存活的 exploit 父进程接管，而不是交给 init。prctl 失败则在 UAF 前退出。
2. 保留成功 UAF 所需的受控 `waitpid`；超时和 post-arm miss 仍禁止收尸。
   stream reclaim 的页分配命中还必须属于当前 exploit PID，避免把其它进程的
   PFN 分配误当成 planting 成功后收尸。
3. **不禁止 zygote 重启**。App 的 LSPosed/Zygisk Next hotfix 继续执行
   `kill -9 zygote64`，不调用会清扫全部用户态的外部 `ksud soft-reboot`。
4. SukiSU late-load 跳过 `INIT_WORK(stop_input_hook_work)`，却在第一次 zygote
   初始化时调度该 work。新增经 ELF 符号和输入哈希锁定的 late-load 模板，
   将无意义的 input-hook cleanup 改为直接返回，避免 `__queue_work` WARNING。
5. hotfix 的 `post-fs-data` 每次开机只在成功后执行一次，避免重复注入
   `lsposed_file`/`magisk_file`；`services` 仍每次运行，zygote 注入不变。
6. 03:03 真机日志显示模块 Build ID 仍为 74ee…：此前 primary
   `ksud late-load --kmi` 未使用已修补文件。现改为默认关闭的显式内置模块开关；
   开启后跳过管理器 KO 提取，走 `ksud insmod $PATCHED`，失败也只直接 insmod
   同一修补资产，不再回退管理器 LKM。内置基线同步更新为上传的 41150 模块。
7. 03:33 运行日志已确认内置模块以 `ksud-insmod-builtin-sukisu-lateload` 成功加载，
   收尾耗时降至约 540ms。03:34 则出现不同的 fatal：zygote exec 时 PC 跳到
   非法地址，LR 为 `ksu_stop_input_hook_runtime+4`，不再是 `rb_next`。
   原补丁覆盖第一条 ADRP，而第一/第二条指令分别带 ADRP/LDST8 重定位；
   装载时可能再次改写补丁。现将 RET 移到第三条无重定位 TBNZ，并在补丁工具中
   强制拒绝重定位重叠。此项仍需真机复验，不能仅凭静态结果宣称重启已解决。

新资产与 hash 见 `BINARY-SOURCES.md`。离线验证包括生命周期单测、普通用户态
subreaper 接管 harness、Shell 语法以及 SukiSU 模板 `ko_patch MISSING=0`。
这些均不等于真机 UAF/zygote 闭环；在明确批准前不自动执行该高风险实验。

## 2026-11-13 策略更新（soft-reboot guard 改为 opt-in）

- `run98260.sh` 不再在 6.12/6.18 上强制布防
  `/data/adb/ksu/soft_reboot.lock`；现在与 6.1/6.6 一致：
  `MAGICROOT_SOFT_REBOOT_GUARD=1` 才布防，默认放行管理器 soft-reboot。
- 原因：FinaSU 等 Flavor 必须用管理器自己的 `ksud soft-reboot` 跑模块
  post-fs-data/services；旧默认会让该动作在 stop/start 前直接失败。
- 本文记录的 panic 机制没有变化：late-load KSU 的 stop/start 仍可能被
  Honor watchdog 转成硬重启，未证明的 timer-UAF victim 仍可能在 init
  收尸时触发 `page_request` panic。完整重启仍是更安全的恢复方式。
