输入：`20261107133702-base(4).apk`

```text

目标          HONOR MagicPad 3 / CGA-W00

```

参考 README 声称该目标在 2026-11-03 已完成 uid0 + KSU 真机闭环；本次只把它作为参考包自述，没有对应设备复验。分析全程只读解包、DEX 反编译、ELF/DWARF/反汇编和哈希比较，未执行参考脚本/原生载荷，未加载 KO，未触发 UAF。

参考包没有导入 MagicRoot 的运行资产。它只支持 gaaa，不能当作现成的全 6.1 通用后端。

## 2. APK 与 App 控制层

Manifest 只有 Shizuku 权限、Shizuku provider 和一个 MainActivity；查询 KernelSU、SukiSU、BakaSU 等管理器。DEX 反编译得到 `MainActivity`、`ShizukuClient` 和少量自定义 View。

App 启动后把 `assets/ek/` 复制到外部私有目录，再通过 Shizuku 或已有 su 执行：

```text
/data/local/tmp/ekpkg/ek-root.sh <stage>
```

主要阶段为 `plan/status/preflight/deploy/exploit/takeover/verify/clean/run`。运行前记录内存、负载和开机时间，提供日志历史、指纹采集、管理器跳转和结果分类。

可借鉴：显式阶段、日志归档、资产哈希、已有 root 时跳过 exploit。

不应复制：

- `ShizukuClient.runShellBlocking()` 在 binder 消失、日志停滞和 hard timeout 时均可能返回 `0`，不能把进程结束当成功。
- `rootReallyWorks()` 在 `/dev/su` 仅存在时也返回 true，不是 uid0 证明。
- `prepareShell()` 删除其他工具的旧 socket、payload 和工作目录，不能合并进当前链。
- UI 文案中的“自动重启”不构成安全恢复机制，当前项目不采用自动重启。

MagicRoot 继续以日志中的真实 `DONE/FAIL`、rootd uid/gid 证明和 KSU/su 结果判定，不以进程结束代替成功。

## 4. 参考 shell 状态机

```text
ek-root.sh run
  ├─ preflight
  │    ├─ exact release 前缀、boot_id、parked、uptime
  │    └─ SHA256SUMS（但缺工具/条目时可软跳过）
  ├─ deploy
  │    └─ /data/local/tmp/ekroot、/data/local/tmp/k、ksu-jump
  ├─ exploit
  │    ├─ core.so calibrate-a  → slide.txt
  │    ├─ core.so calibrate-b  → page_offset.txt
  │    └─ core.so exploit      → rootd socket
  ├─ takeover
  │    └─ core.so ksu-takeover → rootd 执行 sh /data/local/tmp/k
  │         └─ takeover.sh
  │              ├─ 部署 ksuboot/ktpl/fixups
  │              ├─ insmod 前 setsid jumper.sh
  │              ├─ magiskpolicy + ksu_rules.m6
  │              ├─ insmod ksuboot.ko
  │              ├─ 修 su/SELinux 标签
  │              └─ 恢复全局 Enforcing
  └─ verify
       └─ /dev/su -c id、模块、管理器、boot 标记
```

重要缺陷：

1. rootd 获取阶段主要凭 socket 判定，uid0 证明推迟到 takeover 后。
2. takeover 的 policy/insmod 错误不直接向上传递，仍可能写 done marker。
3. `.rooted_boot` 的位置与配置注释不一致，清理语义不统一。
4. clean 会删除仍可能被 parked payload 映射的 core；与自身 deploy 警告冲突。
5. 成功后 SIGSTOP 名称匹配的 payload 并留下 rootd socket，与当前 listener/parent 模型不同。
6. `permissive ksu` 和 `permissive kernel` 存在于策略中；全局 `Enforcing` 不等于所有域都恢复完整约束。

## 5. core.so：98260 实现

### 5.1 命令和主要函数

识别的命令：`wait`、`calibrate-a`、`calibrate-b`、`exploit`、`su`、`rootd-stop`、`ksu-takeover`、`capcheck`。

| `0x10184a4` | `gk_su` | rootd 客户端 |
| `0x1018868` | `calibrate_base` | direct-map base 投票 |
| `0x1018c64` | `trace_start` | tracefs 事件准备 |
| `0x101900c` | `parse_events` | 64 字节事件记录 |
| `0x1019224` | `stage_write` | 单阶段最多 8 次 plant |

| `0x101a874` | `run_target` | memfd/VMA 与触发线程 |
| `0x101b0b4` | `spray_thread` | socket 写回收 |
| `0x101b21c` | `locker_fn` | 映射属性竞争 |

| `0x101b3c8` | `exec_thread` | POSIX timer 创建/arm/exec |

### 5.2 回收与提权

参考实现使用约 195.3 MiB memfd/VMA、3 个 locker、4096 个 POSIX timer、4650 个 padding timer 和 8 个 spray 线程。`run_plant` 通过 socket pool 写 0x2000 字节载荷，结合 trace 恢复 victim/alias/slab PFN，并检查 `slab_own=31`。

`stage_write` 的模式为 `ZERO/PTR/FAKE`。提权依次泄漏 cred/task、清真实 cred 字段、清 securebits、写 SELinux 和 sig_enforce、安装 fake cred、修正 uid/gid，最后由子进程 `setresuid(0,0,0)` 并回报状态。

这些线程数、内存布局和“每阶段 8 次”只在该参考核心中验证过，不应作为其他内核的全局默认值。当前 blind-reclaim 的全局预算、victim 台账和 same-boot parked guard继续保留。

### 5.4 profile.bin 不是通用化证据

脚本把 `profile.bin` 经 stdin 传给 core，但核心没有对应路径字符串，DWARF 中没有相应配置结构，主流程也未发现读取该结构的代码；fake cred 实际使用 core 内置值。

因此“profile.bin 外置配置”很可能只是遗留/兼容输入，不能据此认为同一 core 可换 profile 支持其他 release。profile 中若干字段还与 `ek-config.sh` 不一致，README 明确要求保留这些历史值。

### 5.5 rootd 安全差异

参考 `serve_rootd` 使用固定 socket、0666、顺序 `popen`，未见 `SO_PEERCRED` 或命令长度限制。当前 MagicRoot rootd 有 peer UID（0/2000）和 4096 字节上限。不回移植参考 rootd。

## 6. ksuboot、ktpl 与 fixups

两个 KO 的 vermagic 都是 gaaa。`ksuboot.ko` 有 17 个普通内核 UND 导入，并通过 kprobe 解析 `kernel_write`、`call_usermodehelper`、`__arm64_sys_init_module`。

`ktpl.ko` 没有普通 UND 内核导入，使用 224 个高地址 `SHN_ABS` 符号。`ktpl.fixups` 包含：

- 224 个 `S`：symtab `st_value` 的文件偏移；
- 219 个 `L`：16 字节跳板中 `slot+8` 的 qword 文件偏移。

ksuboot 用运行时 `_printk` 与内置静态 `_printk` 计算 slide，再对 fixup 指定位置统一加 slide，映射模板并调用 `__arm64_sys_init_module`，失败后回退 `call_usermodehelper`。

该机制只解决**同一构建、同一模板文件**的 boot KASLR：

- 不验证模板 hash、S/L 数量、ELF 结构或 fixup 配对身份；
- 换内核必须同时换地址图、fixups、vermagic 和 ksuboot 内置地址；
- 换当前 KO 后不能沿用参考 fixups。

参考/当前 gaaa CGA 的 224 个同名绝对符号地址全部一致；当前另有 `seccomp_filter_release=0xffffffc0081b0d7c`。当前为 225 ABS / 220 stub，参考为 224 / 219，模块布局不同。

结论：保留当前构建期确定性 rebase + 设备端 `ko_slide_patch`，不引入嵌套模块装载。

## 7. 本次对全部 6.1.x 实施的统一改造

### 7.1 统一 profile 与部署

`KernelLogHelper.PROFILES_6157` 现覆盖 run6157 profile 和 g19a。`shouldStage6157Asset()` 成为唯一 6.1 部署规划器：

- 12 个 CGA 构建只得到自己的 payload、CGA base 和公共 su 工具；
- g7d 只得到 M6 与自己的 payload；
- g19a 只得到旧 61157 所需文件；
- g264 的 legacy loader 仍只归 g264；
- 未知 6.1 release 失败关闭；
- MainActivity 的 payload/CGA 查询与资产筛选均委托到同一表。

这同时修复了 gaaa 首版遗漏 `run6157_full.sh` 部署条件的问题。

runner 只在一个 `case` 中选择 `P6157`，再派生：

```text
B=$D/98260-$P6157
G264_BASE=$D/g264/ksm-$P6157-base.ko
G264_KO=$D/ksm-$P6157.ko
```

所有非 g7d 的 run6157 profile 统一启用成功型 blind-reclaim，不再维护第三份长 release 列表。

### 7.2 已有 root 防重入

UAF 前用带 6 秒超时的真实 `id` 检查：

- `/dev/su`、`/system_ext/bin/su`、`/system/xbin/su`、`/system/bin/su`、`/vendor/bin/su` 和 PATH；
- 当前管理器及 bundled ksud 的 `debug su`。

只有输出包含 `uid=0` 才输出 `98260_EXISTING_ROOT=verified` 并退出；文件存在不算成功。该预检只在 `K6157=1` 时启用，输出写入临时文件而非经管道回读，避免超时后 root 侧子进程持有 stdout 造成悬挂。任意 uid0 提供方只记为 existing root，不冒充 KernelSU 已加载。

### 7.3 部署后完整性门禁

新增 `tools/gen_6157_integrity.py` 和 `main/app/assets/6157-integrity.tsv`。清单由 `tools/kernel_profiles.json` 和实际资产生成，可使用 `--check` 确定性复核。

每个 run6157 profile 必须具有固定行数：

- 普通 CGA：10 项；
- g264：13 项（另含 legacy handoff）；
- g7d：22 项（payload/su/sigparam + 19 个 M6 文件）。

runner 在 preflight/UAF 前逐行验证路径、64 位十六进制 SHA-256、文件存在和部署后内容；缺工具、缺条目、数量不符或哈希不符均以 code 74 失败。

### 7.4 CGA 交接加固

- `_printk` 读取、insmod、su 安装均有超时；insmod 默认 60 秒，可由环境覆盖。
- `ko_slide_patch` 必须报告 `abs_symbols=225`、`stub_quads=220`，输出大小必须与 base 相同。
- 记录运行时 patched KO 的 SHA-256；可读 kallsyms 时继续核对 `_printk`。
- M6/CGA 成功后只打开本次 `MAGICROOT_KSU_PKG` 对应的管理器；补齐 KernelSU-Next，不再打开任意已安装 fork。

### 7.5 M6 清理

M6 `post_root.sh` 保留 kptr、kallsyms、dmesg、slabinfo 快照，但不再创建无人消费的 `root:shell 0660` FIFO + `eval` 常驻服务。修改后的 SHA-256：

```text
f3c48e4f0561098a84f4816b63ba88309b8dacf03427bb56c47295f4a146b1d0
```

`m6-provenance.json` 已记录该本地修改。此改动未做 g7d 真机复验。
