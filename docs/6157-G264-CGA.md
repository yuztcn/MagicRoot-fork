# MagicRoot 98260 6.1.157 全链路技术报告

- 日期：2026-11-02
- 范围：`6.1.157-android14-11-g7d3922fade43`（Magic6 系列）与
  `6.1.157-android14-11-g2646292297b1`（HONOR GT / AMG-AN00）
- 交付：MagicRoot 98260 1.0.33-6157（versionCode 40）
- 结论：两个内核构建都已闭环；g264 从「只有临时 root」走到「管理器工作中 + 普通 App
  能通过 su 拿到 uid=0」，并把这套流程封装进 App（1.0.33）。

---

## 0. 一句话结论

CVE-2026-98260 负责把「临时 rootd」打出来；KernelSU LKM 负责长期 root；
g264 的 CGA 复刻模块是 late-load/越狱模式，裁掉了 sucompat，所以普通 App 的 `su`
必须另做：用 KSU 驱动 ioctl `GRANT_ROOT` 写一个 `su_lkm`，再通过 overlay 放进
`/system_ext/bin/su`。1.0.33 把这个过程全部做进 App，g7d3 的 M6 交接保持 1.0.30 原样。

## 2. 总体架构

```text
MagicRoot App
  │  Shizuku (uid=2000)
  ▼
run98260.sh
  │
  ├─ 1) 98260 exploit（g264 用盲写回收版）
  │     └─ 拿到 rootd（uid=0 socket）+ KASLR slide
  │
  ├─ 2) KernelSU LKM
  │     ├─ g7d：M6 ksu_loader.sh / ko_patch2 / load_ko
  │     └─ g264：ksm-g264-base.ko + 手机端 ko_slide_patch → insmod
  │
  └─ 3) su 用户态
        ├─ g7d：M6 自带 /dev/su + su_optional（1.0.30 路径）
        └─ g264：su_lkm（KSU_IOCTL_GRANT_ROOT）+ overlay 到 /system_ext/bin/su
```

关键点：g264 的模块在 init 末尾会把 SELinux 切回 Enforcing，rootd 会被切断；
所以「模块加载后的所有事情」不能再走 rootd，必须走模块自己的 KSU 驱动通道。

## 5. g264 提权：从 page_freed=0 到 rootd

### 5.1 三次失败

- 1.0.26/1.0.27：rootd 一直没起来；1.0.27 还在同一 boot 重试，被 parked 拦截。
- 1.0.28：UAF、task 定位、cred 装填都成功，但 `[stream] hit=0 / page_freed=0`，
  12 次 attempt 全部 miss。
- 1.0.29：加 `blind_reclaim_stream()`，不等 trace，直接按 12 round × 80 write
  把同样的 cred/selinux tile 写进 stream socket；成败交给 rootd 校验。

### 5.2 1.0.30 的 slide empty

1.0.30 在 GT-2 上：

```text
[slide] sample 1/2/3 empty
[slide] measured 0
measurement did not converge, refusing to run
FAIL=proof exec_exited
```

UAF 没开始，但 EXIT trap 仍写 `98260_PARKED=1`，白烧一个 boot。

### 5.3 1.0.31 预检

UAF 前先 `--check --quick` 记录 tracefs/trigger/event；最多 3 次 `--check`；
拿不到就用 dmesg `Kernel Offset` 兜底；全失败就 exit 81，且不写 parked。
1.0.31 的日志显示 `tracefs=1 trigger=1 event=1`、`verdict=ok`，但 slide 还是 0。

### 5.4 真因：头文件覆盖

反汇编对比：

- 旧正确 g264 二进制（2,216,544 B）：`measure_slide` 里 `cmp x11, #0x108`（264）
- 1.0.29 起的盲写二进制（2,327,648 B）：`cmp x11, #0x118`（280 = g7d）

原因：`uaf_plant_61258.c` 无条件 include `pc98260_target.h`，而
`pc98260_target.h` 又无条件 include `pc98260_target_6157.h`（g7d）；
编译时 `-include pc98260_target_6157_g264.h` 的宏随后被 g7d 头覆盖。

修复：`pc98260_target.h` 按 `PC98260_TARGET_6157_G264` 分派，只包含 g264 头。
重编后 `cmp #0x108`，g264 exploit sha256
`cc0b9693dcdba564585c39dfe3eb386860f1cede4251d0d7aca63d1e51762843`。

### 5.5 1.0.32 的成果

## 6. g264 KSU 模块：CGA 复刻管线

### 6.1 根因

`ksu6157-g264/kernelsu-honor.ko` 其实只是 **g7d 模块改了 vermagic**
（`cmp -l` 只差 11 字节），内部 `task->cred` 用 0x840，而 g264 是 0x838；
init_module 必然挂/复位。

### 6.2 CGA-W00 复刻包

用 CGA-W00 复刻包的预编译对象（`obj/*.o`）重链：

```sh
ld.lld -r -o out/ksm-raw.ko obj/*.o
python3 tools/slim2.py out/ksm-raw.ko out/ksm-s1.ko
python3 tools/offrelink6.py out/ksm-s1.ko out/ksm-r.ko <slide>
python3 tools/rename4.py out/ksm-r.ko out/ksm-g264.ko kernelsu
# vermagic 等长替换 gaaa383620ebf -> g2646292297b1
```

- 符号表 `staging/recon/elf_syms.txt` 来自 `vmlinux_g264.elf`（106,608 符号）；
- `offrelink6.py` 把每个未定义符号写成 `SHN_ABS = 链接地址 + slide`；
- 远距离 CALL26 建 220 个跳板（`.text.ksustub`，每个 16 字节：
  `movz/movk` + `br` + 8 字节绝对地址）；
- 225 个符号全解析，0 missing；
- 产物 418,176 B，vermagic `6.1.157-android14-11-g2646292297b1`。

验证：223 个真实内核符号逐一核对 = g264 链接地址 + slide，0 错；
KCFI typeid 是哈希，不是地址；`__flush_icache_range` / `__flush_dcache_area`
走别名。

### 6.3 真机结果

2026-11-01 22:14（boot `1f6a5d6b`，slide `0x23c1200000`）：

- 模块里烘死的 `_printk = 0xffffffe3c98bc710`，与手机 kallsyms 逐位一致；
- `insmod_rc=0`，KernelSU 显示「工作中 [越狱模式]」/ LKM / 32680-5；
- 部署脚本最后 `LOADED=0` 是**假阴性**：模块 init 把 SELinux 切回 Enforcing，
  rootd socket 被切断，脚本再用 rootd 查 `/proc/modules` 就得到
  `connect root daemon: Permission denied`。模块实际已加载。

## 7. g264 实权：为什么 `su` 还是不行

### 7.1 模块裁掉了 sucompat

CGA 模块源码 `hookmgr.c`：

```c
pr_info("L6a: syscall hooks SKIPPED\n");
...
pr_info("L6a: setuid/sucompat SKIPPED\n");
```

late-load 分支不调用 `ksu_ksud_init()`，`sucompat` 明确关闭；系统里没有
`/system/bin/su`，普通 App 的 `ProcessBuilder("su","-c",...)` 直接
`No such file or directory`。管理器「超级用户」开关只是 allowlist，不等于 App
能找到 su。

### 7.2 试过但失败的路径

| 尝试 | 结果 | 原因 |
|---|---|---|
| `su_direct` 直接 `setresuid(0,0,0)` | `EPERM` | 该 kprobe 对 shell 没放行/没注册；源码里 regs[0]=0 也会被真实 syscall 覆盖 |
| `ksud` 改名 `su`，走 argv[0] su 模式 | uid=2000 | su 模式依赖内核 sucompat，模块没有 |
| `echo id \| ksud debug su` | **uid=0** | 走驱动 fd/ioctl，不依赖 sucompat |

`ksud debug su` 需要把命令用管道喂进去：aShell 没有 tty，直接敲会看到
「没反应」，其实是根 shell 读到 EOF 退出了。

### 7.3 最终方案：`su_lkm`

```c
int fd = -1;
prctl(0xDEADBEEF, 0xCAFEBABE, 0, &fd, 0);   // 装 [ksu_driver] fd
if (fd >= 0) {
    ioctl(fd, 0x4B01, 0);                    // KSU_IOCTL_GRANT_ROOT
    close(fd);
}
setresuid(0, 0, 0);
setresgid(0, 0, 0);
execl("/system/bin/sh", "sh", ...);
```

- `0x4B01 = _IOC(_IOC_NONE, 'K', 1, 0)`；
- 内核对 `GRANT_ROOT` 的权限检查是 `allowed_for_su()` =
  `is_manager() || ksu_is_allow_uid_for_current(uid)`；
- 模块加载参数 `allow_shell=1`，shell uid 2000 在 allowlist 里；
- App 只要在 KernelSU 里打开「超级用户」，uid 也在 allowlist 里；
- `su_lkm` 静态 417,984 B，sha256
  `7e9ba63ee35849fc1e31d1b72588f601518d7f9562d5bdfca81a4c49910a3f88`。

### 7.4 让 App 找得到 su

App 只认 PATH。用 M6 的 `su_overlay_helper` 对 **pid 1** 和 **zygote64**
的 mount namespace，在 `/system_ext/bin` 上叠一个 tmpfs overlay，里面只有
`su`（即 `su_lkm`），并标成 `u:object_r:system_file:s0`：

```text
SU_OPTIONAL_MOUNT=overlay pid=1 target=/system_ext/bin
SU_OPTIONAL_MOUNT=overlay pid=1687 target=/system_ext/bin
SU_OPTIONAL_LABEL=u:object_r:system_file:s0/u:object_r:system_file:s0
SU_OPTIONAL_OK
```

重启目标 App 后，它从 zygote 继承新 namespace，`su -c "id -u"` 就能命中。
2026-11-01 23:53，荣耀工具箱 v1.0.3 首次显示 **root OK / Root 权限 正常**。

### 7.5 Termux 的 su 不搜索 `/system_ext/bin`（2026-11-04）

Termux 的 `su` 是 termux-tools 的脚本，按固定绝对路径列表探测，
`/system_ext/bin/su` 不在列表里：

```sh
for p in /debug_ramdisk/su /sbin/su /system/sbin/su /system/bin/su \
         /system/xbin/su /su/bin/su /magisk/.core/bin/su
```

所以 overlay 对荣耀工具箱有效，Termux 却仍报
“No su program found on this device.”。g264 分支又明确跳过会修补这个列表的
`su_entry.sh`（`98260_SU_ENTRY=skipped reason=g264_overlay_su`），问题因此一直存在。

1.0.5 起 `su_optional.sh` 在 overlay 成功后调用 `termux_su_patch()`：

- 把 `/system_ext/bin/su`（或实际挂载目标）放到 `for p in` 列表最前；
- 同时写入正在运行的 `com.termux` 进程的 namespace，旧进程无需重启；
- 输出 `SU_OPTIONAL_TERMUX=patched|already|absent|unsupported|failed`。

详见 `docs/adaptation/47-6157-termux-su-entry.md`。

## 8. 1.0.33 封装

### 8.1 手机端按 slide 打模块

g264 的模块按本次开机 slide 烘死地址，不能一个模块通吃。做法：

1. PC 上以 **slide=0** 链出 `ksm-g264-base.ko`（sha256
   `6381ad16a904af8d7d2a702e04994ed22c3fd01c6e00229ec584634034a56c09`）；
2. 手机端 `ko_slide_patch`（静态 aarch64，420,032 B）把：
   - 所有 `SHT_SYMTAB` 里 `SHN_ABS` 的内核地址加上 slide；
   - `.text.ksustub` 里 220 个 8 字节跳板地址加上 slide；
3. 用两个已知 slide 验证：补出来的模块与 PC 现编版**逐 section 完全一致**
   （只有文件尾一段不再被 section 引用的旧 symtab 死数据不同，内核不读）。

`_printk` 校验：patcher 输出 `_printk=0x...`，与 rootd 从 `/proc/kallsyms`
读到的值比对，不一致直接拒绝 insmod。

### 8.2 App 侧改动

- `MainActivity.java` 新增 `ASSETS_G264` 数组：
  `g264/ksm-g264-base.ko`、`g264/ko_slide_patch`、
  `su-g264/su_lkm`、`su-g264/su_overlay_helper`、
  `su-g264/su_optional.sh`、`su-g264/setup_su_app.sh`；
- 部署循环把 `g264/`、`su-g264/` 原样落到 `/data/local/tmp/magic/`；
- `run98260.sh` 在 M6 分支之后、旧 ksu-loader 分支之前新增 g264 分支：
  patch → printk 校验 → `insmod allow_shell=1` →
  `-d /sys/module/kernelsu`（失败再用 `ksud debug su` 探）→
  `echo "sh $D/su-g264/setup_su_app.sh" | ksud debug su`；
- `setup_su_app.sh` 复制 ksud/su_lkm，调 `su_optional.sh enable`，输出
  `SU_OPTIONAL_OK`；
- g7d3 的 M6 分支一行未动，条件 `G7D=1` 优先。

### 8.3 构建

- 服务器 `/root/work/magicroot-app`，`build-legacy.sh`（aapt2 + javac + d8 +
  pack_apk.py + zipalign + apksigner，keystore 同前）；
- versionCode 40，versionName `1.0.33-6157`；
- APK 69,302,013 B，sha256
  `793b43034603138ea21e2862e5f1d75da213f9c142d180259b0b70f7bc67ca08`。

## 12. 限制与下一步

- **一次开机一发**：98260 失败就重启；模块按本次开机 slide 烘死。
