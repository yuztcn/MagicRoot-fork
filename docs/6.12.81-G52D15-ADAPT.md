## 上游修复核对（本轮新增结论）

原始报告：`V4bel/InfinityCore`（Hyunwoo Kim @v4bel，经 linux-distros 报告后
在 oss-security 与 InfinityCore 文档公开）。

| 项 | CVE-2026-98260 | CVE-2026-64560 |
| --- | --- | --- |
| 机制 | 非 leader `exec()` 失败 → `exit_itimers()` 释放 k_itimer 时其 cpu-timerqueue 节点仍在队列 → reap 时 `cleanup_timerqueue()→timerqueue_del()` UAF | 同族：`posix_cpu_timer_del/set/rearm` 与 leader 交换 PID 竞态释放已入队 timer |
| 引入 | `55e8c8eb2c7b`（v5.7，2020） | 同左 |
| 修复 | `acb03d388181` "exec: Cleanup POSIX timers right after de_thread()"（2026-09-11，tglx 整形） | `920f893f735e` "posix-cpu-timers: Prevent UAF caused by non-leader exec() race"（tglx，2026-07-03） |

按修复补丁逐条核对本 build 二进制：

- **98260 修复未合入，漏洞可达。** 修复前 `begin_new_exec()` 在
  `exec_task_namespaces()` 之后才调 `posix_cpu_timers_exit(me)`（exec_mmap
  等失败点之后），`de_thread()` 不清 timer。二进制实测：
  `begin_new_exec`=0xffffffc0803b9a10，`bl exec_task_namespaces`
  在 +0x248（0x3b9c58）、`bl posix_cpu_timers_exit` 在 +0x25c（0x3b9c6c）；
  全镜像 `posix_cpu_timers_exit(_group)` 调用仅 `release_task`×2 +
  `begin_new_exec`×1 三处，`de_thread` 无调用 → UAF 窗口完整。
- **64560 修复（功能性部分）已合入。** `posix_cpu_timer_del`
  （0xffffffc080590c00）与修复后代码逐条吻合：`timer_lock_sighand`
  重试环（0x5c5c `cbz x0, 0x590c40` 回到 pid 查找）、`dmb ishld`
  （0x590c80，`smp_rmb`）、`brk 0x800` WARN、`put_pid`/`it_status`
  后置；`posix_cpu_timer_set/rearm` 同样带重试环。stable tag
  v6.12.81 的源码没有这些改动（`timer_lock_sighand` 不存在），
  该修复来自 AOSP/厂商树对 920f893f735e 的回迁；6.12.58 机型内核
  无此修复（与本仓库 6.12.58 真机验证记录一致）。
- kernel.org 官方 ChangeLog（6.12.59–6.12.81，共 4295 条提交）无任何
  posix-timer/itimer/timerqueue 族修复；stable tag 对比：
  posix-timers.c / posix-cpu-timers.c / lib/timerqueue.c / fs/exec.c /
  kernel/exit.c 在 v6.12.58 与 v6.12.81 间零变化（fork.c 仅 unshare_fs）。

**结论：该内核只适用 98260 链路；64560 路线在本 build 已被修复，
不要把 64560 payload 指向 g52d15。**

### 2026-11-20 追加：CVE-2026-98432（IPv4 TCP inet_opt/ireq_opt UAF）

原始报告/修复：Eric Dumazet，`e3f33b0a1d89` "ipv4: free inet_opt and
ireq_opt after an RCU grace period"（2026-10-01；Fixes 079096f103fa /
c905dee62232）。上游发布的影响表标注 6.12 线修复于 **6.12.113**。

本 build 二进制核对（补丁的两处 kfree→kfree_rcu 改动逐条对照）：

- `inet_sock_destruct`（0xffffffc0802c1218）：0x2c129c
  `ldr x0,[x19+0x360]`（inet->inet_opt）→ 0x2c12a0 `bl kfree`，函数内
  无 `kvfree_call_rcu` 调用；
- `tcp_v4_reqsk_destructor`（0xffffffc0811a56ac）：函数体一行
  `ldr x0,[x0+0xf0]`（inet_rsk(req)->ireq_opt）→ `bl kfree`；
- kernel.org ChangeLog（6.12.59–81）无该修复。

**结论：98432 修复未合入，两处裸 kfree 原样存在，UAF 窗口保留**
（攻击面是带 IPv4 options 的入站 SYN 重传 / tcp_migrate_req 迁移路径，
与本仓库 98260 临时 root 链路无关，不影响本轮适配结论）。

| `GEOM_MEMSTART_ADDR` | `0xffffffc081a0d8c0` | `memstart_addr` |

与已验证构建的结构差异（这是本轮最重要的核对点）：

- 6.12.58 等旧构建里 `alloc_posix_timer()` 被 LTO **内联**进
  `do_timer_create`，分配点记作 `do_timer_create+0xac`；
- 6.12.81 里 `alloc_posix_timer` 是**独立函数**（0xffffffc0802c3aa0，
  do_timer_create 在 +0x80 `bl` 过去），k_itimer 分配点移到
  `alloc_posix_timer+0x28`（GFP 0xdc0 = GFP_KERNEL|__GFP_ZERO）。
  trace 事件记录的是 kmem_cache_alloc 调用点 `_RET_IP_`，所以
  `LINK_ALLOC_TIMER` 必须取 `alloc_posix_timer+0x28`；
- 该函数内还有一个分配点（+0x9c，带 `current->alloc_tag` 换入换出，
  对应 `alloc_posix_timer._alloc_tag` 数据符号）；全镜像
  B/BL/CBZ/CBNZ/TBZ/B.cond/ADR/ADRP/字面量池扫描显示它**没有任何
  入口引用**，不在默认 timer_create 路径上；
- `prepare_creds` 的分配点仍是 `+0x2c`（GFP 0xcc0，cred_jar），
  与全部既有 6.12 构建一致；
- BTF geometry 与 6.12.58 完全一致（`task_struct.cred=0x900`、
  `real_cred=0x8f8`、`k_itimer.it=0x78`、`size=0x100`、
  `cred size=184`、全部 cred 成员偏移相同）。

最终头文件：`binary-sources/98260-6.12/pc98260_target_g52d15.h`
（g142 风格，slab 几何沿用 g142 的种子值——payload 运行期会从
/proc/slabinfo 覆盖，不匹配时 fail-safe）。

## 验证状态

**仅静态适配**：没有运行该 build 的真机，未触发 UAF、未加载 KSU 模块。
`tools/check.sh` 全绿（语法/LF/资产对账/路由表/单测/链路审计）。
首次真机运行（升级到该 OTA 后）应关注：

```text
98260_PROFILE_MATCH=1 profile=g52d15
98260_KSU_PATCH_RC=0 missing=0
98260_REAL_CRED_INPROC_OK=1
98260_SUCCESS=1
```

如果 KASLR/cred 阶段失败，优先核对 `LINK_SELINUX_STATE`、
`LINK_ALLOC_TIMER`（本轮结构变化点）与设备实际 `uname -r` 对应；
不要用其他 6.12 构建的载荷替代。slab 种子值（task/posix_timers
objsize）以真机 /proc/slabinfo 为准，payload 会自行覆盖。
